# Cybersecurity Goal (CSG) -- Skill Workflow

## 1. When to Use This Skill

**Trigger ON** when the user is:
- Deriving cybersecurity goals from damage scenarios and risk treatment decisions
- Formulating security objectives for ISO 21434 TARA (Threat Analysis and Risk Assessment)
- Creating or updating a cybersecurity goal catalogue
- Working with existing damage scenarios (`data/ds.md`) and risk treatments (`data/rt.md`)
- Asking about "cybersecurity goal", "CSG", "security objectives", "what must be protected", "CIA properties", "goal derivation"
- Starting ISO 21434 Clause 15.9 (cybersecurity goals) work
- Translating active risk treatments into technology-agnostic security objectives
- Mapping damage scenarios to security properties (Confidentiality, Integrity, Availability)
- Preparing inputs for cybersecurity requirements (CSR) derivation

**Trigger OFF** when the user asks:
- About cybersecurity requirements or security control implementations (CSR is a **separate skill** - future work)
- About specific technologies, algorithms, or product implementations (e.g., "use AES-256", "implement SecOC")
- About damage scenarios, impact analysis, or SFOP assessment (use `damage_scenario` skill instead)
- About threat scenarios, attack paths, or AFR rating (use `threat_scenario` skill instead)
- About risk treatment decisions or control selection (use `risk_treatment` skill instead)
- General ISO 21434 theory unrelated to cybersecurity goal formulation
- Vehicle design or engineering topics not related to security objectives

**CRITICAL DISTINCTION - CSG vs CSR**:
- **CSG (this skill)**: High-level security objectives defining WHAT must be protected (technology-agnostic, normative "shall" statements)
- **CSR (separate skill)**: Low-level technical requirements defining HOW to protect (specific algorithms, protocols, configurations)

**Example Distinction**:
- ✅ CSG: "The system shall protect location data confidentiality" (WHAT)
- ❌ CSR: "Implement AES-256-GCM encryption with PBKDF2 key derivation" (HOW)

CSR derivation is OUT OF SCOPE for this skill. Use this skill for goals only.

- One CSG may address multiple DS-IDs (1:N) - A single security goal prevents multiple damages

## 3. Cybersecurity Goal Workflow

**Done Criteria**: Every Avoid/Reduce/Transfer-with-mitigation RT-ID has a corresponding CSG entry in `data/csg.md` passing all 9-field schema validation from `references/csg-schema.md`. Every pure Accept / pure Transfer decision is documented in `data/rt.md` without creating or duplicating a claim-driven CSG entry.

Follow these steps to derive and document cybersecurity goals:

### Step 1: Gather Context

**Read prerequisite documents**:
- Open `data/ds.md` and review all damage scenarios with Impact scores (SFOP dimensions)
- Open `data/rt.md` and review all risk treatment decisions (Avoid, Reduce, Transfer, Accept)
- Identify which damage scenarios require active security goals (Avoid/Reduce) vs claims (Accept/Transfer)

**Understand the SFOP-to-CIA Mapping**:

Cybersecurity goals address damage scenarios by protecting CIA properties:

| SFOP Dimension | Score | Primary CIA Property | Typical Goal Pattern |
|----------------|-------|---------------------|---------------------|
| **Safety (S)** | 3-4 | **Integrity (I)** | Validate/authenticate safety functions |
| | | **Availability (A)** | Ensure safety function remains operational |
| **Financial (F)** | 2-3 | **Confidentiality (C)** | Protect payment/business data |
| | 3-4 | **Integrity (I)** | Prevent unauthorized transactions |
| **Operational (O)** | 2-4 | **Availability (A)** | Maintain service/function availability |
| | 3-4 | **Integrity (I)** | Preserve operational functionality |
| **Privacy (P)** | 2-4 | **Confidentiality (C)** | Protect personal data |

**Source**: `references/csg-guide.md` contains the complete SFOP-CIA mapping table and goal templates.

### Step 2: Identify CSG Derivation Requirements by Treatment Type

For **each RT-ID** in `data/rt.md`:

1. **Extract Treatment Decision** from the RT entry:
   - Find the "Treatment Decision" field (Avoid | Reduce | Transfer | Accept)
   - Note the related DS-IDs referenced by this treatment

2. **Apply CSG Derivation Rules**:

| Treatment Shape | CSG Required? | Output Artifact | Purpose |
|----------------|---------------|-----------------|---------|
| **Avoid** | ✅ Yes | CSG (Goal) | Define WHAT must be eliminated, removed, or redesigned |
| **Reduce** | ✅ Yes | CSG (Goal) | Define WHAT the mitigation must achieve |
| **Transfer + active mitigation** | ✅ Yes | CSG + RT claim | Define WHAT the transferred/implemented mitigation must achieve while RT records responsibility and approval |
| **Pure Transfer** | ❌ No | RT claim only | Document responsibility transfer with no new active goal |
| **Accept** | ❌ No | RT claim only | Justify retained risk with no new active goal |

3. **Decision Logic**:
   - **If Treatment = Avoid or Reduce**: Continue to Step 3 (Formulate Goal)
   - **If Treatment = Transfer and RT entry includes implemented/planned mitigation**: Continue to Step 3 and link the resulting CSG to that RT-ID
   - **If Treatment = Pure Transfer or Accept**: Do NOT create a CSG entry; keep the claim in `data/rt.md`

**Example**:
```
RT-IVI-001 [EXAMPLE]: Treatment = Reduce via Encryption
  → CSG Required? ✅ Yes
  → Continue to Step 3

RT-BCK-003 [EXAMPLE]: Treatment = Transfer
  → If supplier only assumes liability with no new mitigation: ❌ No CSG (RT claim only)

RT-OTA-004 [EXAMPLE]: Treatment = Transfer
  → If supplier implements secure update verification on the OEM's behalf: ✅ Yes
  → Continue to Step 3 and link the CSG to RT-OTA-004

RT-IVI-002 [EXAMPLE]: Treatment = Accept
  → CSG Required? ❌ No (RT claim only)
```

**Output of Step 2**: List of RT-IDs requiring CSG derivation (`Avoid`, `Reduce`, and `Transfer` entries that contain active mitigation)

### Step 3: Formulate Goal Statement

**Objective**: Write a clear, verifiable SHALL statement that addresses the damage scenario impact.

**Goal Statement Template**:
```
The [COMPONENT/SYSTEM] shall [PROTECTION ACTION] to [PREVENT/MITIGATE] [DAMAGE SCENARIO].
```

**Protection Action Patterns by CIA Property**:

#### Confidentiality Goal Template
```
The [COMPONENT] shall protect [DATA TYPE] to prevent unauthorized disclosure.
```

**Example**:
> "The connected services platform shall encrypt location data in transit and at rest to prevent unauthorized tracking."

**When to Use**: Privacy impact (P ≥ 2), Financial impact involving data breaches (F ≥ 2)

---

#### Integrity Goal Template
```
The [COMPONENT] shall validate [DATA/MESSAGE] authenticity to prevent [ATTACK TYPE].
```

**Example**:
> "The CAN gateway shall validate message authenticity to prevent injection of malicious commands."

**When to Use**: Safety impact (S ≥ 2), Operational impact involving data corruption (O ≥ 3)

---

#### Availability Goal Template
```
The [COMPONENT] shall maintain [SERVICE/FUNCTION] availability during [ATTACK/FAILURE CONDITION].
```

**Example**:
> "The telematics control unit shall resist network flooding attacks to maintain emergency call (eCall) availability."

**When to Use**: Operational impact (O ≥ 2), Safety impact involving service loss (S ≥ 2)

---

**Goal Statement Quality Checklist**:
- ✅ Uses "shall" (normative requirement, not "should" or "must")
- ✅ Identifies specific component/system (not "the vehicle")
- ✅ States WHAT, not HOW (no AES-256, TLS 1.3, SecOC, etc.)
- ✅ Addresses the damage scenario (clear link to harm being prevented)
- ✅ Verifiable and testable (can write test case to verify goal is met)
- ✅ Technology-agnostic (applies across implementations and product generations)

**Bad Example**:
> "The system should probably use encryption for privacy."

**Why Bad?**:
- Uses "should" (not normative)
- No specific component identified
- Prescribes HOW (encryption) instead of WHAT (protection)
- Vague (no clear verification criteria)

**Output of Step 3**: Goal statement (1-3 sentences) for each damage scenario requiring mitigation

### Step 4: Assign CIA Property

**Objective**: Classify the goal according to CIA triad for traceability and requirement derivation. Use the SFOP-CIA mapping from Step 1.

**CIA Assignment Decision Tree**:

```
Does goal address DATA DISCLOSURE?
(unauthorized access, privacy, leakage)
  ↓ Yes → Confidentiality (C)
  ↓ No

Does goal address DATA/FUNCTION TAMPERING?
(validation, authentication, corruption)
  ↓ Yes → Integrity (I)
  ↓ No

Does goal address SERVICE AVAILABILITY?
(continuity, DoS, failover, recovery)
  ↓ Yes → Availability (A)
```

**Multiple CIA Properties**: If a damage scenario affects multiple SFOP dimensions mapping to different CIA properties, create SEPARATE goals (one CIA property per CSG entry).

**Example**:
```
DS-CAN-001 [EXAMPLE]: Malicious CAN Message Injection
  - Impact: S=4, O=3 (Safety + Operational)
  - SFOP → CIA: S=4 → Integrity, O=3 → Availability

Create TWO goals:
1. CSG-CAN-01 (Integrity): "Validate message authenticity"
2. CSG-CAN-02 (Availability): "Maintain bus availability during attacks"
```

**Output of Step 4**: CIA property assignment (exactly one of C, I, or A) for each goal

### Step 5: Handle Accept / Transfer in `data/rt.md`

**Objective**: Preserve clean boundaries. `data/csg.md` records active goals; `data/rt.md` records claims, approvals, and residual-risk decisions.

**Working rule** (treatment decision table is in Step 2):
- If the project is **doing something** to change the system or lower risk, derive a CSG.
- If the project is only **retaining** or **assigning responsibility for** residual risk, keep it in `data/rt.md` and do not add a `data/csg.md` entry.

**Examples**:
```
RT-IVI-001 [EXAMPLE]: Treatment = Reduce
  → Create CSG-IVI-01 and link Related RT-IDs: RT-IVI-001

RT-EXT-004 [EXAMPLE]: Treatment = Avoid
  → Create CSG-EXT-02 describing what interface/function is removed or redesigned

RT-BCK-007 [EXAMPLE]: Treatment = Accept
  → No CSG entry; keep justification, approval, and review date in data/rt.md

RT-OTA-004 [EXAMPLE]: Treatment = Transfer
  → If supplier owns both mitigation and liability: keep claim in data/rt.md
  → If supplier implements mitigation that must satisfy an OEM goal: derive CSG-OTA-01 and link it to RT-OTA-004
```

**Output of Step 5**: Either (a) a linked active CSG for mitigation-bearing RT entries, or (b) no CSG and a claim that stays authoritative in `data/rt.md`

### Step 6: Cross-Reference and Validate

**Before finalizing**, verify:

**Traceability Checks**:
- [ ] CSG-ID follows format `CSG-[DOMAIN]-[NN]` with valid 2-digit number (01-99)
- [ ] All Related DS-IDs exist in `data/ds.md` (or marked [EXAMPLE] during skill development)
- [ ] All Related RT-IDs exist in `data/rt.md` (or marked [TBD] if RT cycle not complete)
- [ ] At least 1 Related DS-ID is listed (no orphan CSGs)
- [ ] Rationale references at least one Related DS-ID

**Content Quality Checks**:
- [ ] Goal Statement is technology-agnostic (describes "what" not "how")
- [ ] Goal Statement is testable and verifiable
- [ ] CIA Property correctly reflects the security objective
- [ ] CIA Property aligns with SFOP dimensions of Related DS-IDs
- [ ] Cybersecurity Claim field is empty and claims remain in `data/rt.md`
- [ ] Rationale explains why the CSG is necessary (damage prevention)
- [ ] Rationale cites relevant regulations if applicable (UN R155, ISO 21434, GDPR, GB 44495)

**M:N Mapping Validation**:
- [ ] If CSG addresses multiple DS-IDs, Rationale explains the commonality
- [ ] If DS-ID is addressed by multiple CSGs, Goal Statements are distinct and non-overlapping
- [ ] CSG has 1-5 Related DS-IDs (if more than 5, consider splitting)
- [ ] Every DS-ID in catalogue is either addressed by at least one CSG or explicitly handled as an RT-only Accept / pure Transfer decision

**Schema compliance**: See `references/csg-schema.md` for detailed field validation rules (9 required fields).

## 4. Field-by-Field Guidance

### CSG-ID Assignment

**Format**: `CSG-[DOMAIN]-[NN]`

**Numbering rule**: CSG-IDs use **2-digit format** (not 3-digit like TS/RT/DS) because CSGs are higher-level abstractions with fewer entries per domain.

**Example mappings**:
```
DS-IVI-001 [EXAMPLE] (Location Tracking) → CSG-IVI-01 (Location Data Confidentiality)
DS-CAN-001 [EXAMPLE] (Message Injection) → CSG-CAN-01 (CAN Message Integrity)
DS-OTA-001 [EXAMPLE] (Firmware Tampering) → CSG-OTA-01 (OTA Update Integrity)
```

**Domain codes** (7 total, use existing codes from ds.md):
- **CAN**: CAN bus and in-vehicle networking attacks
- **OTA**: Over-the-air update and remote service attacks
- **EXT**: External interface and physical access attacks
- **BCK**: Backend/cloud service and API attacks
- **IVI**: Infotainment application and OS attacks
- **IMM**: Immobilizer and vehicle access control attacks
- **ADAS**: Advanced driver assistance system attacks

**Domain Selection Guidelines**:
- Use the **primary affected domain** from Related DS-IDs
- If CSG addresses multiple domains, use the **most critical** domain (safety > privacy > convenience)
- Document cross-domain applicability in Related DS-IDs and Rationale

**Validation**: CSG-ID numbering is INDEPENDENT of TS/RT/DS numbering (no 1:1 correspondence required).

### Goal Statement Writing

**Structure** (1-3 sentences, typically 2 sentences):
1. **First sentence**: What shall be protected (security property)
2. **Second sentence**: What threats shall be prevented (damage consequence)

**Goal Statement Template**:
```
The [system/component] shall ensure that [security property]. 
The system shall prevent/detect [threat action] that could [damage consequence].
```

**Good example** (Confidentiality):
```
The vehicle system shall ensure that real-time location data and historical travel 
patterns are accessible only to authorized users and services. The system shall 
prevent unauthorized exfiltration, storage, or sharing of location information that 
could enable driver surveillance or movement tracking.
```

**Good example** (Integrity):
```
The vehicle CAN bus architecture shall ensure that messages controlling critical 
driving functions can only originate from authenticated and authorized ECUs. The 
system shall detect and reject malicious or tampered CAN messages that could affect 
vehicle motion control.
```

**Good example** (Availability):
```
The telematics control unit shall maintain emergency call (eCall) functionality 
during network flooding attacks. The system shall ensure availability of safety-critical 
communication channels to emergency services.
```

**Bad example** (too generic):
```
The vehicle shall be secure against all cyber attacks.
```

**Bad example** (prescribes HOW, not WHAT):
```
The system shall use AES-256-GCM encryption with PBKDF2 key derivation (100,000 iterations).
```

### CIA Property Selection

**Selection Guidelines**:

**Confidentiality-focused CSGs**:
- Protect sensitive data from unauthorized disclosure
- Privacy-related goals (location, PII, driver behavior)
- Credential and key protection
- Example: "Location Data Confidentiality"
- SFOP mapping: Privacy (P ≥ 2) → Confidentiality

**Integrity-focused CSGs**:
- Protect data/commands from unauthorized modification
- Authentication and authorization goals
- Code signing and secure boot
- Example: "CAN Message Authentication"
- SFOP mapping: Safety (S ≥ 2) → Integrity, Operational (O ≥ 3) → Integrity

**Availability-focused CSGs**:
- Ensure critical functions remain accessible
- DoS attack prevention
- System resilience and failover
- Example: "Critical ECU Availability"
- SFOP mapping: Operational (O ≥ 2) → Availability, Safety (S ≥ 2) → Availability

**One CIA Property Per CSG** (see Step 4 for the authoritative rule and example). Do not use `primary/secondary` CIA notation inside a single CSG entry.

**Validation**:
- CIA property selection must align with Goal Statement
- CIA property must match the SFOP dimensions of Related DS-IDs
- If DS has Privacy impact → CSG should include Confidentiality
- If DS has Safety/Operational impact → CSG should include Integrity or Availability

### Rationale Documentation

**Format**: 2-4 sentences (typically 3 sentences)

**Structure**:
1. **First sentence**: What damage scenarios motivate this goal (reference DS-IDs)
2. **Second sentence**: Regulatory or standards context (if applicable)
3. **Third sentence**: How this goal prevents the damage

**Rationale Template**:
```
[Threat/damage description and consequence] ([DS-IDs]). 
[Regulatory/standards requirement if applicable]. 
This goal ensures [security property] to prevent [damage type].
```

**Example (Privacy - Confidentiality)**:
```
Unauthorized access to real-time vehicle location data enables continuous driver 
surveillance, stalking, and privacy violations (DS-IVI-001 [EXAMPLE], DS-IVI-002 [EXAMPLE], DS-BCK-001 [EXAMPLE]). 
Location tracking damages comply with GDPR Article 6 requirements for lawful processing 
of geolocation data and China GB 44495 automotive data security regulations. This goal 
ensures location data confidentiality to prevent privacy harm documented in related 
damage scenarios.
```

**Example (Safety - Integrity)**:
```
Malicious CAN message injection could override legitimate ECU commands and cause 
unintended vehicle acceleration, braking, or steering (DS-CAN-001 [EXAMPLE], DS-CAN-003 [EXAMPLE]). 
Message authentication and integrity protection are required by UN R155 Annex 5 
Part A (Vehicle Motion Control). This goal ensures only authorized ECUs can control 
critical driving functions.
```

**Regulatory References to Include**:
- **UN R155**: For vehicle cybersecurity type approval (EU regulation)
- **ISO/SAE 21434**: For automotive cybersecurity engineering processes
- **GDPR**: For privacy and personal data protection (EU)
- **GB 44495**: For automotive data security (China)
- **ISO 26262**: For functional safety interactions
- **SAE J3061**: For cybersecurity guidebook reference

**Validation**:
- Rationale must reference at least one Related DS-ID
- Rationale should explain the CIA Property selection
- Rationale must stay focused on why the active goal prevents damage
- Claim justifications and approvals belong in `data/rt.md`, not in `data/csg.md`
- Regulatory citations must be accurate and relevant

### M:N Mapping Scenarios

**Scenario 1: One CSG Addressing Multiple DS-IDs (1:N)**

**Situation**: Several damage scenarios share the same root cause or security property.

**Example**: DS-IVI-001 [EXAMPLE] (Location Tracking) + DS-IVI-002 [EXAMPLE] (PII Exposure)
- Both address **Privacy (P)** via **Confidentiality (C)**
- Both involve unauthorized access to user data

**Goal Derived**:
```
CSG-IVI-01: Location Data Confidentiality
  Related DS-IDs:
    - DS-IVI-001 [EXAMPLE] (Unauthorized Driver Location Tracking)
    - DS-IVI-002 [EXAMPLE] (Personal Information Exposure)
```

**Rationale**: Single access control goal addresses multiple data exposure scenarios.

---

**Scenario 2: Multiple CSGs Addressing One DS-ID (M:1)**

**Situation**: A single damage scenario affects multiple SFOP dimensions mapping to different CIA properties.

**Example**: DS-CAN-001 [EXAMPLE] "CAN Bus Message Injection"
- **Impact**: S=4 (steering compromise), O=3 (communication disruption)
- **SFOP → CIA**: S=4 → Integrity, O=3 → Availability

**Goals Derived**:
1. **CSG-CAN-01** (Integrity): "The CAN gateway shall validate message authenticity to prevent injection of unauthorized commands."
2. **CSG-CAN-02** (Availability): "The CAN gateway shall detect and mitigate message flooding to maintain bus availability."

**Rationale**: Integrity goal addresses safety impact (corrupted commands), Availability goal addresses operational impact (DoS on communication).

---

**When to use 1:N (one CSG, multiple DS-IDs)**:
- Damage scenarios share the same root cause or security property
- Same CIA triad property applies across multiple damages
- Example: Data confidentiality goals addressing multiple privacy breaches

**When to use M:1 (multiple CSGs, one DS-ID)**:
- Damage scenario is complex and requires defense-in-depth
- Multiple security properties needed (e.g., Confidentiality + Integrity + Availability)
- Different layers of defense (network, application, physical)
- Example: Critical safety functions requiring authentication, authorization, and input validation

## 5. Common Patterns for CSG

### Pattern 1: Privacy Data (IVI Domain) — Confidentiality Goal

**Scenario**: Privacy Impact 3-4 (P ≥ 3), user personal data at risk (contacts, location, biometrics)

**CIA Property**: Confidentiality

**Typical Goal Pattern**:
```
The [COMPONENT] shall protect [DATA TYPE] to prevent unauthorized disclosure.
```

**Example**:
```
CSG-IVI-01: Location Data Confidentiality
Goal Statement: The vehicle system shall ensure that real-time location data 
and historical travel patterns are accessible only to authorized users and services.
```

**Related DS-IDs**: DS-IVI-001 [EXAMPLE] (Location Tracking), DS-IVI-002 [EXAMPLE] (PII Exposure), DS-BCK-001 [EXAMPLE] (Telematics Breach)

**Regulatory driver**: GDPR Article 6 (lawful processing), GB 44495 (personal information protection)

**Example**: `references/examples/example-01-ivi.md` (RT-owned Accept claim with no new CSG entry)

---

### Pattern 2: Safety-Critical (CAN Domain) — Integrity Goal

**Scenario**: Safety Impact 4 (Critical), CAN message injection risk

**CIA Property**: Integrity (create a separate Availability CSG if service continuity must also be protected)

**Typical Goal Pattern**:
```
The [COMPONENT] shall validate [DATA/MESSAGE] authenticity to prevent [ATTACK TYPE].
```

**Example**:
```
CSG-CAN-01: CAN Bus Message Integrity and Authenticity Goal
Goal Statement: The vehicle CAN bus architecture shall ensure that messages 
controlling critical driving functions can only originate from authenticated 
and authorized ECUs.
```

**Related DS-IDs**: DS-CAN-001 [EXAMPLE] (CAN Message Injection), DS-CAN-003 [EXAMPLE] (Gateway Bypass)

**Regulatory driver**: UN R155 Clause 7.2.4.1 (vehicle network protection), ISO 26262 ASIL-D

**Important**: Even with integrity controls (e.g., AUTOSAR SecOC), Residual RV often remains RV 5 because Impact 4 (Critical) dominates the matrix. This is acceptable — controls make the attack practically infeasible even if the matrix value doesn't decrease.

**Example**: `references/examples/example-02-can.md` (CSG-CAN-01: CAN Bus Message Integrity)

---

### Pattern 3: Backend API (BCK Domain) — Separate Confidentiality and Integrity Goals

**Scenario**: Financial/Privacy Impact 3, backend API authorization bypass

**CIA Property**: Split into one Confidentiality CSG and one Integrity CSG when both properties matter

**Typical Goal Pattern**:
```
The [COMPONENT] shall authenticate all [REQUESTS/TRANSACTIONS] to prevent 
unauthorized [ACCESS/MODIFICATION].
```

**Example**:
```
CSG-BCK-01: Backend API Authentication and Authorization
Goal Statement: The backend API shall authenticate all user requests and validate 
authorization before granting vehicle control or data access.
```

**Related DS-IDs**: DS-BCK-001 [EXAMPLE] (API Authorization Bypass), DS-BCK-002 [EXAMPLE] (Data Breach)

**Regulatory driver**: GDPR Article 32 (backend APIs process personal data), OWASP API Security Top 10

---

### Pattern 4: OTA Updates (OTA Domain) — Separate Integrity and Availability Goals

**Scenario**: Safety/Financial Impact 4, firmware manipulation risk

**CIA Property**: Integrity for update authenticity; create a separate Availability CSG for rollback/recovery if needed

**Typical Goal Pattern**:
```
The [COMPONENT] shall verify [FIRMWARE/SOFTWARE] authenticity to prevent 
installation of unauthorized updates.
```

**Example**:
```
CSG-OTA-01: Secure OTA Update Integrity
Goal Statement: The OTA update system shall ensure that only cryptographically 
signed and verified firmware images from the authorized manufacturer can be 
installed on vehicle ECUs.
```

**Related DS-IDs**: DS-OTA-001 [EXAMPLE] [EXAMPLE] (Firmware Tampering), DS-OTA-003 [EXAMPLE] [EXAMPLE] (MITM Attack)

**Regulatory driver**: UN R155 Clause 7.3.1 (secure software update mechanisms), ISO 21434 Table 13

---

### Pattern 5: Multi-DS Goals (Cross-Domain) — Defense-in-Depth

**Scenario**: Multiple damage scenarios across domains share common security property

**CIA Property**: Confidentiality (data protection across multiple attack vectors)

**Typical Goal Pattern**:
```
The [SYSTEM-WIDE COMPONENT] shall implement [SECURITY PROPERTY] to prevent 
[DAMAGE TYPE] across [DOMAINS].
```

**Example**:
```
CSG-IVI-01: Location Data Confidentiality (Cross-Domain)
Related DS-IDs:
  - DS-IVI-001 [EXAMPLE] (Infotainment app exfiltration)
   - DS-BCK-001 [EXAMPLE] (Backend API breach)
   - DS-EXT-001 [EXAMPLE] (USB malware access)
```

**Rationale**: All three damage scenarios involve location data breaches through different attack vectors. A single CSG for "Location Data Confidentiality" addresses the root security property needed to prevent all three damages.

## 6. Quality Checks

Before finalizing your cybersecurity goal catalogue, perform these quality checks:

### Cross-Reference Validation

- **Check 1**: All DS-IDs referenced in `data/csg.md` exist in `data/ds.md`
- **Check 2**: All RT-IDs referenced in `data/csg.md` exist in `data/rt.md`
- **Check 3**: CIA property of each CSG aligns with SFOP dimensions of its Related DS-IDs

### Schema Compliance

**Check all CSG entries have 9 required fields**:
- [ ] CSG-ID (format: CSG-[DOMAIN]-[NN], 2-digit number)
- [ ] Title (max 80 chars)
- [ ] Related DS-IDs (valid references, at least 1)
- [ ] Related RT-IDs (valid references or marked [TBD])
- [ ] Goal Statement (1-3 sentences, "shall" language, technology-agnostic)
- [ ] CIA Property (Confidentiality | Integrity | Availability)
- [ ] Cybersecurity Claim field left empty (claims stay in `data/rt.md`)
- [ ] Rationale (2-4 sentences, references DS-IDs, cites regulations)
- [ ] Last Updated (YYYY-MM-DD)

**Reference**: `references/csg-schema.md` contains detailed validation rules for each field.

### Treatment Decision Consistency

**Check CSG creation aligns with Risk Treatment**:
- Avoid treatments → CSG exists and describes what was eliminated/redesigned ✓
- Reduce treatments → CSG exists and describes what mitigation must achieve ✓
- Transfer with active mitigation → CSG exists and links to RT-ID; claim remains in `data/rt.md` ✓
- Pure Transfer / Accept → no CSG required; justification and approval remain in `data/rt.md` ✓

- RV 1-2 scenarios → May have Accept treatment with formal documentation ✓

**Check RT-owned claims instead of duplicating them in `data/csg.md`**:

## 8. Troubleshooting

### Issue 1: Don't know which CIA property to assign

**Symptom**: Damage scenario has multiple SFOP dimensions (e.g., S=3, F=3, O=2, P=1). Unclear which CIA property applies.

**Solution**: Use the SFOP-CIA mapping matrix from Step 1 (Section 3) or `references/csg-guide.md`. If multiple CIA properties apply, create MULTIPLE goals (one per CIA property).

**Example**:
```
DS-CAN-001 [EXAMPLE]: S=4, O=3
  → Create TWO goals:
     CSG-CAN-01 (Integrity): Prevent message tampering (addresses S=4)
     CSG-CAN-02 (Availability): Ensure bus availability (addresses O=3)
```

### Issue 3: Where should claim documentation live?

**Symptom**: User asks "Should I fill in the Cybersecurity Claim field for this Reduce / Accept / Transfer treatment?"

**Clarification**: Under this skill's policy, the `Cybersecurity Claim` field in `data/csg.md` stays empty for all CSG entries. Formal claim text, approvals, and residual-risk rationale belong in `data/rt.md`.

| Treatment Shape | CSG Claim Field | Why? |
|----------------|-----------------|------|
| **Avoid** | EMPTY | Goal documents elimination/redesign; no claim required |
| **Reduce** | EMPTY | Goal documents active mitigation |
| **Transfer + active mitigation** | EMPTY | Goal documents active mitigation; RT documents transfer claim |
| **Pure Transfer** | No new CSG | RT alone documents transfer claim |
| **Accept** | No new CSG | RT alone documents acceptance claim |

**Key Rule**: If you are actively mitigating risk, create a CSG and leave the claim field empty. If you are only retaining or assigning responsibility for risk, keep the claim in `data/rt.md` and do not create a new CSG.

### Issue 4: User asks about cybersecurity requirements (CSR)

**Symptom**: User asks "What are the specific security controls for this goal?" or "Should I specify TLS 1.3 or TLS 1.2?"

**Response**: This skill covers **cybersecurity goals (CSG)** only. Cybersecurity requirements (CSR) are a **separate skill** (future work).

**Skill boundaries**:
- **csg** (this skill): Documents high-level security objectives (WHAT must be protected), technology-agnostic shall-statements, CIA property assignment
- **Cybersecurity Requirements (CSR)** (separate skill): Specifies concrete technical requirements (HOW to protect), specific algorithms, protocols, configurations

**Workflow order** (ISO 21434 Clause 15):
1. Cybersecurity Goals (CSG) → defines "Protect confidentiality of location data" as security objective
2. Cybersecurity Requirements (CSR) → specifies "Implement AES-256-GCM encryption with PBKDF2 key derivation" as implementation requirement

**What to document in cybersecurity goals**:
- Security objective (e.g., "protect data confidentiality")
- CIA property (Confidentiality)
- **NOT** specific algorithms, key sizes, or products

**Redirect user**: "CSR specification will be covered in a separate skill. For now, focus on WHAT must be protected (goal), not HOW to protect it (requirement)."
